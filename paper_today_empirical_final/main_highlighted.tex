\begin{abstract}
Reliable execution in multi-agent desktop automation requires robust error mitigation beyond raw task scheduling. Real-world automation workflows routinely encounter application crashes, missing file dependencies, transient network timeouts, and \chg{unauthorized operations}. Existing AI agent recovery approaches rely heavily on continuous model-based replanning, \chg{which can introduce inference latency, token usage, and behavioral variability.} In this paper, we present the self-healing subsystem of Phoenix Agents, a deterministic, bounded recovery framework designed to diagnose and remediate execution exceptions in multi-agent desktop workflows without requiring an active Large Language Model (LLM) during the recovery loop. The recovery mechanism is structured into five operational stages: error parsing, root-cause classification, strategy selection, patch generation, and retry execution. Recovery decisions follow typed contract assertions, deterministic rules, and a fixed retry budget ($K_{\text{max}} = 3$). \chg{Empirical evaluation across 125 controlled fault-injection trials (25 per class across five fault categories) demonstrates that the pipeline achieved a 66.7\% recovery rate (50/75, Wilson 95\% CI: [55.4\%, 76.3\%]) across the 75 recoverable-by-design faults (recovering 25/25 Timeout and 25/25 Missing Resource, while Tool/Adapter faults were rejected as unmapped), and safely rejected all 50 non-recoverable faults (100.0\%, Wilson 95\% CI: [92.9\%, 100.0\%], $n=50$) across Permission/Policy Violation and Unmapped/Unknown Exception. Overall recovery across all 125 faults was 40.0\% (50/125, Wilson 95\% CI: [31.8\%, 48.8\%]), with an 80.0\% total correct decision rate (100/125, Wilson 95\% CI: [72.1\%, 86.1\%]), compared to 20.0\% (25/125) for naive retry and 0.0\% (0/125) for fail-fast. Mean recovery latency was 2.06~ms (median 1.98~ms) on mocked adapters and 2.30~ms for real-filesystem missing resource synthesis.}
\end{abstract}

\section{Introduction}
Multi-agent desktop and browser automation frameworks orchestrate complex workflows across web browsers, native applications, operating system terminals, and local file systems~\cite{bajoria2026}. However, executing tasks across heterogeneous host environments inherently exposes software agents to dynamic execution failures, such as transient network timeouts, missing file dependencies, altered DOM locators, process crashes, and permission denials.

In conventional script-based automation systems (e.g., Selenium, AutoHotkey), a single runtime exception causes catastrophic workflow failure. While recent research explores self-healing via Large Language Models (LLMs)---such as reflective prompt loops and continuous model replanning---each LLM call in recovery incurs latency and token cost that depend on the model and prompt size, along with safety risks from uncontrolled retries~\cite{babu2026,jeong2026}.

\chg{To address these challenges, we present the deterministic self-healing architecture of Phoenix Agents.} Phoenix Agents uses an in-process asynchronous publish--subscribe EventBus for event delivery, while the five recovery stages execute sequentially within the recovery handler. The framework uses a lightweight 5-stage pipeline (Error Parsing, Root-Cause Analysis, Strategy Selection, Patch Generation, and Retry Execution) that diagnoses and remediates execution errors without requiring an active LLM runtime during error recovery.

The Primary Technical Contributions of This Paper:
\begin{itemize}
    \item \textbf{Structured 5-Stage Self-Healing Pipeline:} A modular recovery architecture executing error parsing, root-cause diagnosis, strategy selection, patch generation, and retry dispatch without LLM inferencing delays.
    \item \chg{\textbf{Deterministic In-Process Recovery Loop:} Rule-based mitigation policies and typed contract assertions achieving millisecond-scale handling latency (mean $T_R = 2.05$~ms, $T_{\text{rec}} = 2.06$~ms on mocked adapters; 2.30~ms on real filesystem).}
    \item \chg{\textbf{Bounded Retry \& Safety Guard Policy:} Strict enforcement of a maximum retry limit ($K_{\text{max}} = 3$) paired with safe rejection of non-recoverable operations (100.0\% safe rejection over 50 non-recoverable faults, Wilson 95\% CI: [92.9\%, 100.0\%], $n=50$).}
    \item \chg{\textbf{Empirical Verification Across 125 Controlled Trials:} Controlled fault-injection evaluation across 125 trials (25 per class across five classes), reporting both the aggregate recovery rate (40.0\%, 50/125, Wilson 95\% CI: [31.8\%, 48.8\%]; 80.0\% correct decision rate, 100/125) and the recoverable subset rate (66.7\%, 50/75, Wilson 95\% CI: [55.4\%, 76.3\%]) side-by-side, establishing clear differentiation against naive retry (20.0\% overall recovery; 0.0\% safe rejection).}
\end{itemize}

\section{Related Work}

\subsection{Self-Healing Agent Orchestrators and LLM Recovery}
Recent studies explore self-healing mechanisms to improve the operational reliability of tool-augmented Large Language Model (LLM) agents. Babu and Agrawal proposed self-healing orchestrators for LLM tool agents, emphasizing reflective prompt loops for fault correction~\cite{babu2026}. Jeong and Shin investigated autonomous self-healing frameworks for LLM agents~\cite{jeong2026}. Patel et al.\ explored predictive self-healing using Model Predictive Control (MPC)~\cite{patel2026a} and multi-agent learning~\cite{patel2026b}. While these approaches improve adaptability, invoking generative models during error recovery inherently incurs latency and token cost that depend on the underlying model and prompt size, alongside potential variability in recovery decisions.

\subsection{Fault-Tolerant Multi-Agent Collaboration}
In multi-agent systems, fault tolerance research addresses role drift, agent disagreements, and dynamic environment reconfigurations. Wang et al.\ developed lightweight protocols to detect and repair role drift in collaborative multi-agent workflows~\cite{wang2026}. Ju et al.\ investigated self-repair capabilities elicited under LLM multi-agent disagreements~\cite{ju2025}. Guo et al.\ introduced EvoConfig for self-evolving multi-agent configuration~\cite{guo2026}. Bara et al.\ demonstrated self-healing multi-agent pipelines for machine learning workflows~\cite{bara2026}. Phoenix Agents complements this line of research by addressing discrete workflow execution exceptions through structured fault taxonomies and bounded deterministic rules.

\subsection{Web and GUI Automation Reliability}
In web and desktop automation, fault recovery historically focused on dynamic locator repair and selector maintenance during UI test execution~\cite{garcia2026}. Surveys by Nguyen et al.~\cite{nguyen2025} and Bajoria et al.~\cite{bajoria2026} highlight that GUI agents frequently fail due to unhandled ambient operating system noise, dynamic DOM updates, and transient network delays. Traditional GUI testing frameworks lack dependency-aware task graphs and supervisory contracts required for autonomous, multi-application workflow recovery.

\subsection{Research Gap \& Key Differentiation}
Existing self-healing literature focuses primarily on model-driven reflection or continuous replanning~\cite{babu2026,jeong2026,patel2026a}. These approaches often rely on generative replanning where each LLM invocation adds model-dependent latency and cost, and they frequently lack strict safety guards, resulting in uncontrolled retries of unsafe system operations. Phoenix Agents bridges this gap by decoupling error diagnosis from LLM runtime inferencing, executing a 5-stage bounded recovery pipeline sequentially within the recovery handler to achieve millisecond-scale \chg{recovery latency (mean $T_R = 2.05$~ms, $T_{\text{rec}} = 2.06$~ms) alongside 100.0\% safe rejection of non-recoverable operations.}

\section{Proposed Solution: 5-Stage Deterministic Self-Healing Architecture}
The proposed self-healing subsystem of Phoenix Agents is designed as an in-process, deterministic recovery framework that remediates execution exceptions without invoking active LLM inference during the recovery loop. Normal workflow dispatch and fault handling are kept as decoupled, specialized subsystems communicating asynchronously over the publish--subscribe EventBus.

\subsection{Formal Problem Formulation \& Recovery Objectives}
Let a workflow execution graph be represented as a Directed Acyclic Graph $G = (V, E)$. When the Supervisor Agent audits post-execution task outputs $O_i$ against contract assertions $\Psi(v_i, O_i)$, any failure triggers an observed execution fault tuple:
\begin{equation}
F = (E_{\text{err}}, C_{\text{ctx}}, S_{\text{workflow}})
\end{equation}
where $E_{\text{err}}$ represents the captured exception traceback, $C_{\text{ctx}}$ represents execution parameters and tool adapter state, and $S_{\text{workflow}}$ is the atomic graph lifecycle state.

The recovery objective function $R(F)$ maps observed faults to either permitted remediation actions or safe terminal rejections:
\begin{equation}
R(F) =
\begin{cases}
A_{\text{retry}}, & \text{if } F \in \mathcal{C}_{\text{recoverable}} \land k_i < K_{\text{max}}, \\
A_{\text{reject}}, & \text{if } F \in \chg{\mathcal{C}_{\text{nonrec}}} \lor k_i \ge K_{\text{max}}.
\end{cases}
\end{equation}
where $k_i$ is the retry counter for task $v_i$, $K_{\text{max}} = 3$ is the maximum allowed retry budget, $A_{\text{retry}}$ applies deterministic parameter patching or \chg{backoff retry}, and $A_{\text{reject}}$ triggers safe failure escalation.

\subsection{Detailed 5-Stage Recovery Pipeline Breakdown}
The self-healing workflow is executed sequentially across five specialized, in-process software modules:

\subsubsection{Stage 1: Error Parser (\texttt{error\_parser.py})}
Intercepts published \texttt{task.failed} event payloads and parses unhandled stack traces into structured error objects, extracting error strings, failing module paths, adapter bindings $\tau_i$, and payload parameters $\theta_i$.

\subsubsection{Stage 2: Root-Cause Analyzer (\texttt{root\_cause\_analyzer.py})}
Evaluates parsed error objects against deterministic rule sets to classify faults into a 5-tier taxonomy:
\begin{equation}
\mathcal{C} \in
\begin{Bmatrix}
\chg{\text{Timeout}, \quad \text{Missing Resource}}, \\
\chg{\text{Tool/Adapter Failure}}, \\
\chg{\text{Permission/Policy Violation}}, \\
\chg{\text{Unmapped/Unknown Exception}}
\end{Bmatrix}
\end{equation}

\subsubsection{Stage 3: Recovery Planner (\texttt{recovery\_planner.py})}
Evaluates whether the classified fault is recoverable and checks retry budget constraints ($k_i < K_{\text{max}}$). If $k_i \ge K_{\text{max}}$ or if the fault is classified as \chg{non-recoverable (Permission/Policy Violation, Unmapped/Unknown Exception)}, it marks the task as unrecoverable and emits a \texttt{task.rejected} event.

\subsubsection{Stage 4: Patch Generator (\texttt{patch\_generator.py})}
Constructs the required corrective action using the selected deterministic recovery strategy:
\begin{itemize}
    \item \textbf{Exponential Backoff:} Calculates delay $\Delta t = 2^{k_i} \times 1.0\,\text{s}$ for Timeout faults.
    \item \textbf{Parameter Patching:} Corrects missing file paths or parameters in $\theta_i$ by inspecting ancestor task outputs in graph $G$ \chg{or synthesizing target resource paths.}
    \item \textbf{Adapter Substitution:} Queries \texttt{ToolRegistry} for a functional substitute adapter $\tau'_i$ for Tool/Adapter Failure faults.
\end{itemize}

\subsubsection{Stage 5: Retry Engine (\texttt{retry\_engine.py})}
Applies generated patches, increments retry counter $k_i \leftarrow k_i + 1$, resets task status $S_i \leftarrow \text{READY}$, and dispatches a typed \texttt{task.retry} \chg{event over the EventBus.}

\section{Methodology and Implementation}
The self-healing architecture of Phoenix Agents is implemented as a modular \chg{Python package} integrated directly within the execution engine kernel.

\subsection{Asynchronous In-Process Event Backbone (EventBus)}
Phoenix Agents uses an in-process asynchronous publish--subscribe EventBus for event delivery, while the five recovery stages execute sequentially within the recovery handler. The EventBus is constructed over Python's native \texttt{asyncio} event loop. Rather than incurring network IPC delays, event objects are published directly to memory channels.

When a tool adapter fails, the Worker Agent publishes a strongly typed \texttt{task.failed} event containing:
\begin{equation}
\text{Payload} = \langle \text{task\_id}, \tau_i, \theta_i, e_{\text{exception}}, \text{traceback\_str} \rangle
\end{equation}
Handler callbacks in the Healing Agent process events asynchronously as non-blocking coroutines without stalling concurrent DAG task branches.

\subsection{Supervisory Contract Verification Engine (SupervisorAgent)}
Before a task is marked as completed, the Supervisor Agent evaluates tool execution artifacts $O_i$ against pre-registered contract assertions:
\begin{align}
\Psi(v_i, O_i) = (\text{exit\_code} == 0) &\land (O_i \models \text{Schema}(v_i)) \nonumber \\
&\land (\text{FileExists}(O_i))
\end{align}
If any assertion evaluates to false, the Supervisor transitions the node status $S_i \leftarrow \text{FAILED}$ and publishes the failure diagnostic payload to trigger self-healing.

\subsection{Fault Taxonomy \& Pattern Matching Classifier (\texttt{root\_cause\_analyzer.py})}
\chg{The Root-Cause Analyzer processes exception strings using deterministic rule matching across a 5-tier taxonomy: recoverable faults comprise \textit{Timeout} (mitigated via bounded retry with exponential backoff), \textit{Missing Resource} (parameter/path correction from ancestor task outputs or directory creation), and \textit{Tool/Adapter Failure} (intended for adapter substitution via \texttt{ToolRegistry}); non-recoverable faults comprise \textit{Permission/Policy Violation} and \textit{Unmapped/Unknown Exception}, both mapped to immediate safe rejection and failure escalation.}

\subsection{\chg{Parameter Patching \& Adapter Resolution (\texttt{patch\_generator.py})}}
\begin{itemize}
    \item \textbf{Parameter Patching:} For Missing Resource faults, the Patch Generator inspects ancestor node output dictionaries in graph $G$ to resolve valid target file paths \chg{or synthesizes missing directory trees within workspace boundaries.}
    \item \textbf{Adapter Substitution:} For Tool/Adapter Failure faults, the component queries \texttt{ToolRegistry} to resolve a functional substitute adapter $\tau'_i$. \chg{In our evaluated 125-fault benchmark suite, injected tool failures used unmapped command error strings that were classified as unknown and safely rejected; adapter substitution was evaluated in separate component unit tests.}
\end{itemize}

\section{Empirical Evaluation \& Experimental Results}

\subsection{\chg{Experimental Setup}}
\chg{All experiments were conducted on a workstation equipped with an AMD Ryzen 7 8845HS processor (16 logical execution threads), 15.26~GB RAM, running Windows 11 Home (build 10.0.26300) and Python 3.14.4.} 

\chg{The evaluation suite comprised 125 controlled fault injections (25 distinct faults per class across five classes):}
\begin{enumerate}
    \item \chg{\textit{Timeout} (25 faults, recoverable by design);}
    \item \chg{\textit{Missing Resource} (25 faults, recoverable by design);}
    \item \chg{\textit{Tool/Adapter Failure} (25 faults, recoverable by design);}
    \item \chg{\textit{Permission/Policy Violation} (25 faults, non-recoverable);}
    \item \chg{\textit{Unmapped/Unknown Exception} (25 faults, non-recoverable).}
\end{enumerate}
\chg{The test workloads comprised 3--5 task Directed Acyclic Graphs generated from 10 distinct task templates ($\approx 25$ workflows). Each trial was executed across two injection modes:}
\begin{itemize}
    \item \chg{\textbf{Synthetic Mode:} The faulted task returns an execution failure payload carrying simulated error tokens and module tracebacks.}
    \item \chg{\textbf{Real Exception Mode:} Real Python exceptions (e.g., \texttt{TimeoutError}, \texttt{FileNotFoundError}, \texttt{PermissionError}) are raised through \texttt{ErrorParser}.}
\end{itemize}
\chg{Adapters were bypassed for faulted execution attempts. Across all 125 faults, synthetic and real exception injection modes produced identical downstream diagnostic and recovery decisions (100\% parity).}

\chg{To evaluate repeatability, each configuration was executed across 30 independent randomized repeats with seeds 42 to 71. The random seed modifies synthetic payload identifiers and instance ordering; because Phoenix executes deterministic rule-based state transitions without generative model queries, every seed produced identical outcomes. The independent statistical unit is the distinct fault ($n=25$ per class, $n=75$ for the recoverable pool, $n=50$ for the non-recoverable pool, and $n=125$ for the full suite); Wilson 95\% score confidence intervals are reported with respect to these distinct fault counts.}

\chg{\textit{Evaluation Disclosure:} During experimental audit, three classification and policy defects were identified and resolved: (i) a confidence-boundary condition failing to reject unknown faults at confidence $\le 0.30$, (ii) a missing-path recoverability block in \texttt{RetryEngine} that prevented directory creation, and (iii) a permission-signal ordering error that misclassified permission denials on nonexistent paths as missing directories. All reported results reflect the post-fix codebase; the 50-fault set used during debugging served strictly as a diagnostic set, not as a blind held-out evaluation.}

\subsection{\chg{Recovery and Safe Rejection Accuracy}}
\chg{Four primary accuracy metrics characterize the system:}

\subsubsection{\chg{Recoverable-Case Success Rate ($SR_{\text{rec}}$)}}
\chg{Measures recovery success strictly across the 75 recoverable-by-design faults (Timeout, Missing Resource, Tool/Adapter Failure):}
\begin{equation}
\chg{SR_{\text{rec}} = \frac{N_{\text{recovered,rec}}}{N_{\text{injected,rec}}} \times 100 = \frac{50}{75} \times 100 = 66.7\%}
\end{equation}
\chg{with a Wilson 95\% confidence interval of [55.4\%, 76.3\%] ($n=75$). Phoenix successfully remediated 25/25 Timeout faults and 25/25 Missing Resource faults. For Tool/Adapter Failure, the harness injected unmapped command failure strings (\texttt{COMMAND\_FAILED}), which were assigned confidence $\le 0.30$ and safely rejected (0/25 recovered, 25/25 rejected).}

\subsubsection{\chg{Safe Rejection Rate ($SR_{\text{safe}}$)}}
\chg{Measures the proportion of non-recoverable faults (Permission/Policy Violation, Unmapped/Unknown Exception, $N_{\text{injected,nonrec}} = 50$) correctly identified and terminated without initiating unauthorized retries:}
\begin{equation}
\chg{SR_{\text{safe}} = \frac{N_{\text{rejected,nonrec}}}{N_{\text{injected,nonrec}}} \times 100 = \frac{50}{50} \times 100 = 100.0\%}
\end{equation}
\chg{with a Wilson 95\% confidence interval of [92.9\%, 100.0\%] ($n=50$). All 25 Permission/Policy Violations were blocked by monotonic policy checks, and all 25 Unmapped/Unknown Exceptions were safely rejected under the $\le 0.30$ confidence rule.}

\subsubsection{\chg{Overall Recovery Ratio ($SR$)}}
\chg{Measures the proportion of all 125 injected faults resulting in automated recovery:}
\begin{equation}
\chg{SR = \frac{N_{\text{recovered}}}{N_{\text{injected}}} \times 100 = \frac{50}{125} \times 100 = 40.0\%}
\end{equation}
\chg{with a Wilson 95\% confidence interval of [31.8\%, 48.8\%] ($n=125$). Because 50 faults represent non-recoverable security and unmapped errors, the theoretical maximum recovery rate on this benchmark is 60.0\% (75/125).}

\subsubsection{\chg{Total Correct Decision Rate ($SR_{\text{decision}}$)}}
\chg{Measures the combined proportion of correctly recovered recoverable faults and correctly rejected non-recoverable faults:}
\begin{equation}
\chg{SR_{\text{decision}} = \frac{50 + 50}{125} \times 100 = 80.0\%}
\end{equation}
\chg{with a Wilson 95\% confidence interval of [72.1\%, 86.1\%] ($n=125$).}

\subsection{\chg{Comparison with Baseline Systems}}
\chg{Table~\ref{tab:empirical_recovery_rates} summarizes performance across Phoenix, Naive Retry, and Fail-Fast:}
\begin{itemize}
    \item \chg{\textbf{Naive Retry Baseline:} Re-executes the failed task up to $K_{\text{max}} = 3$ times without error parsing or state patching. Naive Retry recovers Timeout faults as effectively as Phoenix (both 25/25, 100.0\%), as transient timeouts clear upon re-execution. However, Naive Retry achieves 0/25 (0.0\%) on Missing Resource, because blind re-execution cannot create missing directories or repair corrupted paths. On Tool/Adapter Failure, Naive Retry also achieves 0/25 (0.0\%). Across all 75 recoverable faults, Naive Retry recovers 25/75 (33.3\%, Wilson 95\% CI: [23.7\%, 44.6\%]). Critically, on the 50 non-recoverable faults, Naive Retry executes $3 \times 50 = 150$ unauthorized retries before terminal failure (0.0\% safe rejection, 0/50, Wilson CI: [0.0\%, 7.1\%]). Overall recovery is 20.0\% (25/125, Wilson CI: [13.9\%, 27.9\%]).}
    \item \chg{\textbf{Fail-Fast Baseline:} Immediately halts workflow execution upon encountering an exception. It achieves 0/75 (0.0\%, Wilson CI: [0.0\%, 4.9\%]) recovery on recoverable faults, safe rejection on all 50 non-recoverable faults (100.0\%, Wilson CI: [92.9\%, 100.0\%], $n=50$), and 0/125 (0.0\%, Wilson CI: [0.0\%, 3.0\%]) overall recovery.}
\end{itemize}

\subsection{\chg{Recovery Latency Distribution}}
\chg{Recovery latencies were measured with background telemetry tracing disabled (\texttt{PHOENIX\_TRACE=0}) to eliminate disk write overhead. Table~\ref{tab:latency_breakdown} reports latency distributions across two demarcated intervals:}
\begin{itemize}
    \item \chg{\textbf{Diagnostic Handling Latency ($T_R$):} Measures in-process execution across Stages 1--5 (error parsing, root-cause analysis, strategy planning, patch generation, and task re-enqueue). Evaluated across $n=1500$ observations (30 repeats of 50 recovered trials) on mocked adapters, $T_R$ recorded a mean of 2.05~ms, standard deviation (SD) of 0.69~ms, median of 1.98~ms, interquartile range (IQR) of 0.71~ms, and an empirical range of 1.03--11.84~ms.}
    \item \chg{\textbf{Total Recovery Duration ($T_{\text{rec}}$):} Measures the complete interval from task dispatch through failure detection, diagnosis, mocked worker re-execution, and supervisor contract validation. Across $n=1500$ observations, $T_{\text{rec}}$ recorded a mean of 2.06~ms, SD of 0.69~ms, median of 1.98~ms, IQR of 0.72~ms, and range of 1.03--11.85~ms.}
    \item \chg{\textbf{Real Filesystem Missing Resource Latency:} Standard trials use mocked adapters without disk I/O. To measure physical disk I/O overhead on Windows NTFS, real directory synthesis and file artifact writes were measured across 100 independent trials. Real-filesystem recovery recorded a mean of 2.30~ms, SD of 0.25~ms, median of 2.29~ms, IQR of 0.28~ms, and range of 1.74--3.17~ms ($n=100$).}
    \item \chg{\textbf{Fail-Fast Duration ($T_{\text{no\_rec}}$):} Recorded a mean of 0.001~ms (median 0.001~ms, $n=3750$). Because the fail-fast baseline merely transitions an in-memory task status flag to \texttt{FAILED} without attempting diagnostic parsing or remediation, subtracting it from $T_{\text{rec}}$ is non-informative.}
\end{itemize}

\subsection{\chg{Concurrency Determinism \& Qualitative LLM Comparison}}
\subsubsection{\chg{Concurrency Audit (Experiment D)}}
\chg{To evaluate thread safety and shared-state determinism under concurrent multi-workflow execution, 10 concurrent workflows executing tasks across a shared \texttt{SelfHealingLoop} instance were evaluated over 30 repeats ($R=30$). Across all 30 runs, concurrent task execution outcomes matched sequential reference execution 100.0\% (30/30, Wilson 95\% CI: [88.7\%, 100.0\%]). State clobbering was 0 events, and failure signature collisions were 0 events, verifying that per-task state tracking and scoped retry counters eliminate shared-state race hazards.}

\subsubsection{\chg{Qualitative Comparison with LLM-Based Orchestrators}}
\chg{Because active LLM-based agent orchestrators were not benchmarked head-to-head within this local desktop environment, comparison with published LLM approaches remains qualitative. As documented in prior literature~\cite{babu2026,wu2025}, LLM-based recovery approaches rely on generative reflection prompts and iterative re-prompting. While generative models provide flexible reasoning for novel error descriptions, each model call incurs hundreds of milliseconds to several seconds of network and inferencing latency, non-deterministic outputs across identical seeds, and recurring token costs. Phoenix Agents targets predictable execution exceptions in desktop automation, offering sub-3-millisecond deterministic handling for known fault classes.}

\subsection{\chg{Limitations}}
\chg{Several operational limitations should be highlighted:}
\begin{enumerate}
    \item \chg{\textbf{No Blind Held-Out Evaluation:} Although a held-out template structure was prepared, no blind held-out evaluation was conducted. The 50-fault auxiliary set was utilized strictly as an internal diagnostic suite to detect classification and policy defects.}
    \item \chg{\textbf{Tool/Adapter Failure Handling:} In the 125-fault benchmark suite, injected tool failures used unmapped command error strings that were rejected as unknown ($\le 0.30$ confidence); dynamic adapter substitution was verified only in isolated component unit tests and was not demonstrated in the benchmark suite.}
    \item \chg{\textbf{Scope of Determinism:} Deterministic guarantees apply to in-process rule classification, parameter patching, and retry budget enforcement. End-to-end multi-agent behavior in arbitrary desktop environments remains subject to external operating system nondeterminism and third-party software crashes.}
\end{enumerate}

\section{Conclusion and Future Work}

\subsection{Conclusion}
This paper presented the bounded self-healing subsystem of Phoenix Agents, a deterministic, LLM-free recovery framework for multi-agent desktop automation. By isolating error parsing, root-cause diagnosis, strategy selection, patch generation, and retry dispatch into an in-process 5-stage pipeline, the system remediates execution exceptions without invoking active LLM inferencing during error recovery.

Key \chg{empirical} findings demonstrate:
\begin{enumerate}
    \item \chg{\textbf{Millisecond-Scale Recovery Handling:} The pipeline achieved a mean handling latency $T_R$ of 2.05~ms and total recovery duration $T_{\text{rec}}$ of 2.06~ms on mocked adapters, with real-filesystem directory repair averaging 2.30~ms.}
    \item \chg{\textbf{Fault Recovery on Recoverable Faults:} Across 75 recoverable-by-design faults, Phoenix recovered 50/75 (66.7\%, Wilson 95\% CI: [55.4\%, 76.3\%]), successfully repairing 25/25 Timeout and 25/25 Missing Resource faults, while unmapped Tool/Adapter faults were safely rejected.}
    \item \chg{\textbf{100.0\% Safe Rejection Rate:} Across 50 non-recoverable faults (Permission/Policy Violation and Unmapped/Unknown Exception), safety guards safely rejected all 50 non-recoverable operations (100.0\%, Wilson 95\% CI: [92.9\%, 100.0\%], $n=50$) without unauthorized retries.}
    \item \chg{\textbf{Overall Recovery and Baseline Contrast:} Overall recovery across all 125 faults was 40.0\% (50/125, Wilson 95\% CI: [31.8\%, 48.8\%]), with an 80.0\% correct decision rate (100/125), substantially exceeding Naive Retry (20.0\% overall recovery; 0.0\% safe rejection) and Fail-Fast (0.0\% recovery; 40.0\% correct decision rate).}
\end{enumerate}

\subsection{Future Work}
\chg{Future research will expand Phoenix Agents along four primary directions:
(1)~\textit{Topological DAG Replanning Integration:} integrating runtime dynamic subgraph pruning and Kahn-based topological dependency re-sorting into the core execution engine;
(2)~\textit{Adapter Substitution Mapping:} registering comprehensive adapter error signatures in \texttt{ErrorParser} to route live tool crashes to alternate adapter implementations;
(3)~\textit{Real Browser \& Desktop Chaos Testing:} evaluating recovery under dynamic DOM locator shifts, live network latency degradation, and host process terminations; and
(4)~\textit{Safe Checkpoint Rollback:} developing transactional checkpointing mechanisms to enable atomic state rollback for complex multi-application workflows.}
